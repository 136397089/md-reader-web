## 背景与痛点

基础全文搜索（issue 001）上线后，进阶用户需要：正则匹配、大小写敏感、按目录范围搜索、以及保留搜索历史避免重复输入。

## 功能描述

在 001 基础上扩展搜索能力与历史记录。

## 实现方案

- 后端 `/api/search` 增加参数：
  - `regex=true` — 启用正则（注意 DoS 防护，限制复杂度 / 超时）
  - `case_sensitive=true`
  - `path=<scope>` — 限定搜索目录范围
- 前端搜索框增加切换项（正则 / 大小写 / 范围）
- 搜索历史：`localStorage` 存最近搜索词，下拉展示，可清除

## 涉及文件

- `src/routes.py` — 扩展 `/api/search` 参数与匹配逻辑
- `src/static/app.js` — 高级选项 UI、搜索历史
- `src/static/app.css` — 选项与历史样式
- `src/translations.py` — 相关文案

## 资源需求与体验影响分析

### 服务端（重点：ReDoS 与 CPU）
- **继承 001 的全部服务端压力**，并因正则而放大：
  - **ReDoS（正则拒绝服务）**：用户构造的恶意/病态正则（如 `(a+)+`）在特定输入上指数级回溯，**单次请求可卡死一个 Werkzeug 线程数秒甚至更久**，多线程被耗尽则全站无响应。必须：限制正则复杂度、设单次匹配超时（Python `re` 无原生超时，需用信号或第三方 `regex` 库的 `timeout`，或限定正则长度/嵌套）。
  - **范围搜索**限定目录可减少扫描量，是性能正向。
- **CPU**：正则比纯字符串匹配贵，结果上限 + 超时保护仍是硬性要求。

### 客户端
- 搜索历史走 `localStorage`，与 003/004/005 共用配额，需限条数。
- **体验影响**：**正向（面向进阶用户）**，但正则一旦不加超时保护，会从"功能"变成"服务稳定性漏洞"。基础版(001)未做正则正是明智之举。

## 备注

必须在 001 完成后开展。**正则必须做 ReDoS 防护 + 单次匹配超时，否则威胁全站可用性。**
