## 背景与痛点

当前安全模型存在两处待改进：

1. **密码硬编码**：`config.py` 中 `PASSWORD = 'grant91'`，明文写死在源码，部署/更密码不便，且有泄露风险（已在 git 历史中）。
2. **单用户模型**：所有人共享同一密码、同一目录视图，无法区分用户与权限。

面向「部署给多人使用」的场景需要演进。

## 功能描述

1. 密码改为通过环境变量 / `.env` 注入，源码不再含明文。
2. （可选增强）支持多用户，每个用户独立的可见目录与凭据。

## 实现方案

### 阶段一：密码环境变量化（低风险，先做）
- `config.py` 改为 `PASSWORD = os.environ.get('MARKDOWN_READER_PASSWORD', '')`
- 启动时校验：未设置则警告或拒绝启动
- 提供密码哈希存储（bcrypt / argon2），`verify_password` 改为哈希比对
- README / Docker Compose 文档更新（`docker-compose.yml` 加 env 示例）
- 历史明文密码纳入 `.gitignore` 思路说明（git 历史另议）

### 阶段二：多用户（高成本，按需）
- 用户配置文件（用户名 → 哈希密码 + 允许的根目录）
- 登录态记录当前用户，`base_dir` 按用户切换
- 各 API 的路径校验基于用户根目录

## 涉及文件

- `src/config.py` — 密码读取方式
- `src/utils.py` — `verify_password` 改哈希比对
- `src/routes.py` — （阶段二）按用户切换 `base_dir`
- `docker-compose.yml` / `Dockerfile` — 环境变量注入
- `README.md` — 部署说明更新

## 验收标准

### 阶段一
- [ ] 源码不再含明文默认密码
- [ ] 密码经环境变量注入，未设置时有明确提示
- [ ] 密码以哈希形式校验
- [ ] 现有登录流程不受影响

### 阶段二（如开展）
- [ ] 支持多用户独立凭据
- [ ] 用户间目录隔离，路径越权被拒
- [ ] 会话与用户绑定

## 资源需求与体验影响分析

### 服务端
- **阶段一（密码环境变量化）**：哈希校验（bcrypt/argon2）单次约几十毫秒 CPU，仅登录时发生一次，可忽略；反而比当前明文 `==` 比对更安全，无额外常驻开销。
- **阶段二（多用户）**：每用户独立根目录会增加文件系统遍历的隔离复杂度，但单请求资源量不变；会话需绑定用户身份，session 存储略增。

### 客户端 / 体验
- **阶段一**：用户无感知，登录流程不变；但**修复了一个真实安全漏洞**（明文密码已进 git 历史），属于"不做就有风险"的必选项。
- **阶段二**：多用户会改变登录与目录语义，需谨慎评估是否真有多人场景，否则属过度设计。**建议阶段一优先独立落地，阶段二按需。**

## 备注

阶段一应优先于阶段二；明文密码已在 git 历史中，部署到生产前务必更换。涉及现有 RSA 加密登录链路，改动需回归测试。**阶段一为安全必选项，可独立先行。**
