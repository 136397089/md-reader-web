## 背景与痛点

当前侧边栏只能逐级浏览目录，**查找内容只能逐个点开文件**。文档数量增多后，定位某段文字非常低效，这是阅读类工具的第一缺失功能。

## 功能描述

支持在所有 `.md` 文件中搜索关键字，返回匹配的文件与匹配行，点击结果可跳转到对应文件并高亮定位。

## 实现方案

### 后端
- 新增 API：`GET /api/search?q=<keyword>&case_sensitive=<bool>`
- 在 `base_dir` 下递归遍历 `.md` / `.markdown` 文件，逐行匹配
- 返回结构：`{ results: [{ file, line_no, line_preview, snippet }] }`
- 复用 `utils.is_safe_path` 做路径校验，结果文件须通过安全检查
- 需考虑性能：可限制返回结果数（如 top 50），超大文件跳过或截断

### 前端
- 侧边栏顶部增加搜索输入框（带快捷键 `/` 或 `Ctrl+K` 唤起）
- 结果列表展示文件名 + 匹配行预览，匹配关键字高亮
- 点击结果调用 `openFile()`，并滚动到对应行（配合行号锚点）

## 涉及文件

- `src/routes.py` — 新增 `/api/search` 路由
- `src/static/app.js` — 搜索框交互、结果渲染、跳转逻辑
- `src/template/main_template.py` — 侧边栏加入搜索框 DOM
- `src/translations.py` — 新增搜索相关文案（占位符、无结果、结果数等）

## 验收标准

- [ ] 输入关键字可跨所有 Markdown 文件检索
- [ ] 结果展示文件名与匹配行上下文，关键字高亮
- [ ] 点击结果打开文件并定位到匹配位置
- [ ] 路径越权请求被拒绝（安全）
- [ ] 无结果时有友好提示

## 资源需求与体验影响分析

> ⚠️ 这是本批需求中**对服务端资源压力最大**的一项，需重点设计。

### 服务端（CPU / 内存 / I/O）
- **CPU 密集 + 阻塞风险**：搜索需在 `base_dir` 下递归读取并逐行扫描所有 `.md` 文件。本项目运行在 **Werkzeug 开发服务器 + `threaded=True`**（单进程多线程），一次全量搜索可能扫描成百上千个文件、读入数十 MB 文本，**单次请求耗时数百毫秒到数秒**，期间占用一个工作线程，高并发下会拖慢其他所有请求（文件浏览、图片加载）。
- **I/O 放大**：每次搜索都重读全部文件，磁盘 I/O 随文件总量线性增长。
- **内存**：若一次性读入所有内容再搜索，大文档库会瞬时占用大量内存。

### 缓解策略（必须做）
1. **结果数上限**：找到 N 条（如 50）即提前终止，不全量扫描。
2. **行级流式读取**：逐文件逐行扫描，不一次性载入全文。
3. **超时保护**：单次搜索设硬超时（如 3s），超时返回「部分结果 / 结果过多请细化」。
4. **去抖**：前端输入 debounce（300–500ms），避免每键一请求。
5. **（可选进阶）索引缓存**：维护文件 mtime → 内容的内存索引，仅变更文件重扫；或用 `ripgrep`/系统 grep 外部进程加速。一期可不做，但需在文件量增大时纳入路线。

### 客户端（网络 / 渲染 / 体验）
- **网络**：结果 JSON 体积取决于预览长度，需限制每条 snippet 字符数。
- **渲染**：结果列表大量 DOM 节点会拖慢滚动，建议虚拟滚动或限制渲染条数。
- **体验影响**：这是**最高频的"找不到内容"破局点**，做好后整体"可用性"质变；但若首版不加去抖/上限，在弱网或大库下反而会让用户感觉"卡"，必须配套做缓解策略。

### 安全资源考量
- 搜索范围严格限制在 `base_dir` 内，复用 `is_safe_path`；正则模式（issue 010）需额外防 ReDoS，基础版用纯字符串 `in` 匹配即可。

## 备注

可作为后续「正则搜索 / 大小写敏感 / 搜索历史」（issue 010）的基础。**实现时务必先落地"结果上限 + 去抖 + 超时"三件套**，否则会拖垮整体响应。
